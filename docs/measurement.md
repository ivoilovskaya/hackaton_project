# Цель 1. Тестовые данные и правила измерения

Статус: спецификация MVP и контрольный synthetic-пример. Это проектные допущения для кейса, а не результаты реальной рекламы. Программный расчёт и полный набор для 20 каналов — следующие этапы.

## Что измеряем

Цепочка: channel → placement → creative → touch → lead → purchase → revenue.
Единица отчёта — отдельное размещение. Один канал может иметь несколько размещений; один креатив может использоваться повторно.

## Схема данных

| Таблица | Обязательные поля |
|---|---|
| placements | placement_id (уникальный), campaign_id, channel_id, publication_time, cost, currency |
| placement_creatives | placement_id, creative_id, tracking_token (уникальный) |
| touches | touch_id (уникальный), visitor_id, placement_id, creative_id, touch_time |
| leads | lead_id (уникальный), visitor_id, student_id, lead_time |
| purchases | purchase_id (уникальный), student_id, purchase_time, amount, refunded_amount, status |

Время — ISO 8601 с часовым поясом, в примере UTC; деньги — RUB. В производственном расчёте хранить деньги в копейках или Decimal.
Все синтетические наборы маркировать is_synthetic=true. Не смешивать их с реальными продажами.

## Как передать источник

Для каждой пары placement_id/creative_id выдаём отдельную ссылку на собственный redirect endpoint с tracking_token. Сервер по токену находит campaign/channel/placement/creative, фиксирует переход и перенаправляет на лендинг. Токен не содержит персональных данных.

На лендинге сохраняем visitor_id; при регистрации связываем его со student_id. Оплата содержит тот же student_id. Просто UTM-меток без этой связи недостаточно. Переходы с другого устройства не связываем автоматически: нужна авторизация или иное подтверждённое сопоставление.

## Атрибуция MVP

- Last paid touch: для каждой успешной оплаты выбираем последний переход этого пользователя в интервале [purchase_time − 7 суток, purchase_time].
- При одинаковом времени выбираем touch_id по возрастанию для воспроизводимости.
- Источник лида определяем отдельно: последний переход за 7 суток до lead_time.
- При отсутствии подходящего перехода источник — unattributed; расходы рекламы на него не распределяем.
- Каждая покупка относится максимум к одному размещению. Повторные покупки учитываем по уникальным purchase_id.
- Возврат уменьшает выручку исходного размещения. Неоплаченные/отменённые заказы не включаем.
- Семь суток — выбранное допущение, его можно изменить; это не доказательство причинного эффекта рекламы.

## Период отчёта

Для сравнения размещений выбираем когорту по publication_time и наблюдаем переходы в течение 7 суток после публикации (включая начало, исключая конец). Покупки наблюдаем до 7 суток после каждого такого перехода. Выбор последнего перехода выполняем по всей доступной истории, затем фильтруем выбранный источник по когорте: иначе возможна ложная атрибуция.
Полный горизонт созревания когорты — 14 суток после публикации. Более ранний отчёт помечаем предварительным. Возвраты учитываем по состоянию на явно указанную дату выгрузки.

## Метрики по размещению

| Метрика | Правило |
|---|---|
| Переходы | Количество уникальных touch_id в окне наблюдения |
| Посетители | Количество уникальных visitor_id среди этих переходов |
| Лиды | Количество уникальных student_id с атрибутированным лидом |
| Покупатели | Количество уникальных student_id с атрибутированной успешной покупкой |
| Покупки | Количество уникальных успешных purchase_id |
| Чистая выручка | Сумма amount − refunded_amount по атрибутированным покупкам |
| CPL | cost / лиды |
| Стоимость покупателя | cost / покупатели; не называем CAC без проверки, что клиент новый |
| Конверсия посетителя в покупателя | покупатели / посетители × 100% |
| ROAS | чистая выручка / cost, коэффициент |
| ROMI | (маржинальный доход до рекламных расходов − cost) / cost × 100% |

Для demo маржинальный доход = чистая выручка × 0.60. Маржа 60% — исключительно тестовое допущение; реальное значение нужно получить от бизнеса. При отсутствии маржи выводим ROAS, а ROMI оставляем неизвестным. При нулевом знаменателе выводим null/«не определено», не ноль. Неизвестная стоимость также null, а не 0.

Уникальных покупателей по каналам и кампании пересчитываем, а не складываем из строк размещений. Стоимость размещения не дублируем при соединении с событиями или креативами. Для ROMI отдельного креатива нужен согласованный способ распределения стоимости; пока рассчитываем ROMI только по размещению.

Без сопоставимых данных о просмотрах/показах CTR и CPM не рассчитываем.

## Контрольный пример

См. [measurement_fixture.json](../data/mock/measurement_fixture.json). Все записи синтетические; пример иллюстрирует правила, не заменяет полный тестовый набор.

- p01: расходы 1000, 2 посетителя, 2 лида, 1 покупатель, чистая выручка 5000; CPL 500; стоимость покупателя 1000; конверсия 50%; ROAS 5; ROMI при марже 60% = 200%.
- p02: расходы 2000, 1 посетитель, 0 лидов, 1 покупатель, чистая выручка 3000 после возврата 1000; CPL не определён; стоимость покупателя 2000; конверсия 100%; ROAS 1.5; ROMI = −10%.
- Оплата u03 на 700 не атрибутирована.
- u01 сначала пришёл из p01 и стал лидом, затем перешёл из p02 и купил: источник лида и покупки различается.

## Полный synthetic-набор: следующий этап

Сгенерировать воспроизводимый набор с фиксированным seed: 20 каналов, минимум 2 размещения на канал, минимум 3 креатива. Включить размещения без продаж, повторные покупки, несколько источников у пользователя, покупку без перехода, переход старше 7 суток, покупку ровно на границе 7 суток, возврат, дубликат события, нулевую и неизвестную стоимость.

Проверки: уникальность ключей; существование связанных ID; переход не раньше публикации; сумма возврата от 0 до суммы оплаты; отсутствие двойного учёта; сумма выручки размещений и unattributed равна всей включённой чистой выручке. Полностью возвращённая успешная покупка сохраняется в числе покупок и покупателей, её чистая выручка равна нулю.

## Как получить исторические размещения

Запросить реестр закупок у команды: канал, ссылка на пост, дата/время, стоимость и валюта, кампания, креатив, подтверждающий источник. Предложить CSV-импорт с проверкой обязательных полей, дублей и отчётом об ошибках.
Счета и переписка могут подтвердить расходы. Публичные посты сами по себе не подтверждают цену. Неизвестные значения не выдумывать.
Без исторических идентификаторов переходов связь старой оплаты с рекламой достоверно не восстановить; совпадение дат недостаточно.
